사용자 지적: ① 결혼하는 부부 입장에서 결혼 준비부터 결혼 이후까지 전부를
다뤄야 한다 ② UI는 처음부터 다시 — 폰에서 쉽게 볼 수 있게 ③ Gantt가
아니어도 된다.

반성: 5절이 "뷰는 Gantt가 중심"을 모든 보드에 강제했다. Gantt는 짧고 병렬
폭이 넓은 실행형 보드(위성 웨이브)에 맞는 뷰였을 뿐, 사람이 폰으로 들고
다니며 "지금 뭘 해야 하지"를 확인하는 수개월 여정에는 맞지 않는다. 또
웨딩 보드에서 MC-01이 7건으로 상한(6건)을 넘겼듯, 소수 인원이 긴 기간을
가는 프로젝트에서 총량 상한은 사람을 허구로 늘리게 만든다.

산출물:
- RULES.md v3.3 — ① 5절: **뷰는 하나가 아니다** — 보드 자료(JSON)는 한
  벌이고, 뷰는 도메인과 이용자에 맞게 고른다(Gantt는 기본 뷰 중 하나).
  어떤 뷰든 검사(취합·시각·입력 추적)는 같은 자료 위에서 동일하게 작동
  한다. 폰 우선. ② 4절: 역할 상한 6건은 **한 단계(웨이브) 안**의 몫이다 —
  동시 TAKEN 1건은 언제나 유지.
- tools/build_journey_view.py — 폰 우선 "여정" 뷰: 진행 링·지금 할 일·
  단계별 접이식 카드·바텀시트 상세(왜 사슬). Gantt 없음.
검증: examples/journey(부부 관점 결혼 전체 여정 보드)로 실증 — 상견례부터
결혼 이후 정리까지, 입력 추적 경고 0, 폰 스크린샷.

검증: examples/journey 완주(46건·경고 0) — 부부 발행 단계 6개, 요청 13건,
잠정→정정 1건(대출 한도), 단계당 상한 실측 최대 4건. 여정 뷰를 폰
뷰포트(390px)·다크 모드에서 확인, 바텀시트 왜 사슬 작동. 기존 웨딩 보드
(66건)도 같은 뷰어로 즉시 렌더됨(자료·그리기 분리의 증거).
검증: 여정 보드 완주(46건·경고 0) + 폰·다크 확인, 웨딩 보드 재사용 렌더 확인
